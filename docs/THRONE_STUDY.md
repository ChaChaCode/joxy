# Что JOXY берёт из Throne — подходы, не код

Throne (github.com/throneproj/Throne, коммит 32ee312 от 1 ноября 2026) и nekoray распространяются под GPL-3.0. Их исходники лежат в `../upstream/` только для чтения. Код, функции и фрагменты оттуда в JOXY не копируются, иначе JOXY станет GPL-проектом. Мы переносим идеи и решения, а реализуем своими словами и своим кодом.

## Происхождение

- Ядра: V2Ray (2015) → Xray-core (2020, форк V2Ray; VLESS, REALITY, XHTTP). sing-box (2022, SagerNet) написан с нуля.
- Оболочки: Qv2ray (Qt, закрыт) повлиял на nekoray (MatsuriDayo, архив с 12.12.2024). Throne — прямое продолжение nekoray.
- JOXY — самостоятельная оболочка над Xray, как в своё время nekoray над V2Ray.

## Как устроен Throne

- Два процесса: интерфейс (C++/Qt) и ядро `ThroneCore` (Go). Они общаются по локальному IPC.
- ThroneCore встраивает sing-box и Xray как библиотеки, а не запускает их отдельными exe.
- **sing-box** создаёт TUN, ведёт маршрутизацию и DNS. **Xray** нужен только для протоколов, которых нет в sing-box (XHTTP и т. п.). Связь между ними идёт через локальный SOCKS-мост: sing-box → мост → Xray → сервер.
- Kill switch — отдельный процесс того же exe (`ThroneCore --guard`). Его запускает интерфейс и держит открытым его stdin.
- В Windows для TUN весь интерфейс перезапускается с правами администратора. Так же делает и JOXY.

## Уроки, отсортированные по пользе для JOXY

### 1. Kill switch и блокировки — через динамическую сессию WFP, без журналов
`core/internal/guard/backend_windows.go`, `wfp_windows.go`

- Фильтры WFP добавляются в сессию с флагом `FWPM_SESSION_FLAG_DYNAMIC`. Когда процесс завершается, даже аварийно, Windows сама удаляет все его правила. Журнал восстановления и watchdog не нужны: оставить систему без интернета невозможно в принципе.
- Все правила ставятся одной транзакцией (`FwpmTransactionBegin/Commit`). При ошибке не остаётся ничего.
- Своя подсистема (sublayer) с максимальным весом. Порядок правил: разрешить своё приложение по AppID (`FwpmGetAppIdFromFileName0`) → разрешить TUN-адаптер по LUID → loopback → (по желанию) локальная сеть → DHCP/NDP → заблокировать всё остальное.
- DNS к локальной сети (порты 53/853) блокируется даже при разрешённой LAN: роутер отправит запрос в обход туннеля.
- Каждые 5 секунд проверяется, что правило «заблокировать всё» на месте. Если служба BFE перезапустилась или правило удалили, kill switch сообщает о взломе.
- Сменился LUID адаптера (новый `throne-tun 2` после сбоя) → разрешение для TUN переставляется атомарно.
- Процесс-страж завершается, когда закрыт stdin или умер родитель. На Windows это `WaitForSingleObject` на дескрипторе родителя, без опроса.

**Для JOXY:** прямо тянуть WFP из Node.js неудобно. Реалистичный вариант — маленький собственный помощник на Go или C#, по устройству как `--guard`. Это закрывает пункт 0.4.0 «kill switch» и убирает целый класс ошибок вроде бага `File.Replace` в 0.3.2.

### 2. TUN строит ядро, а не скрипты
`src/configs/generate.cpp` (`buildInboundSection`, `buildRouteSection`)

- В sing-box `tun` задаются `auto_route: true`, `strict_route`, `mtu`, адреса IPv4/IPv6 и `route_exclude_address` (127.0.0.0/8, 255.255.255.255/32, частные сети, пользовательские исключения). Маршруты, DNS адаптера и защиту от утечек ставит само ядро и само же убирает при остановке.
- DNS: правило `{"protocol":"dns","action":"hijack-dns"}` плюс `sniff` перехватывают любые DNS-запросы, попавшие в TUN.
- `route.auto_detect_interface: true` — исходящие соединения сами следуют за текущим интерфейсом по умолчанию.

**Для JOXY:** сейчас маршруты 0.0.0.0/1 и 128.0.0.0/1, DNS адаптера и WeakHostSend ставит `windows-tun.ps1`, а снимает журнал восстановления. Это самый хрупкий участок. Варианты:
- (а) встроенный TUN Xray с его автомаршрутами, если в 26.x их хватает на Windows (проверить);
- (б) добавить sing-box как второе ядро только для TUN, по схеме Throne: sing-box TUN → SOCKS → наш Xray.

Оба варианта убирают PowerShell из пути подключения.

### 3. Смена сети: следовать за интерфейсом и пересоздавать пулы
`core/internal/netmon/netmon.go`, `core/internal/xray/gate.go` (`Recycle`), `core/internal/rpc/egress.go`

- Постоянный монитор интерфейса по умолчанию (sing-tun `DefaultInterfaceMonitor`) держит актуальный исходящий интерфейс. TUN и loopback из кандидатов исключены.
- Xray-инстанс при смене сети пересоздаётся. Без этого пулы XHTTP, gRPC и mux висят на ушедшей сети, пока не истекут их собственные проверки.
- Новый инстанс запускается рядом со старым, старый закрывается только после успешного старта (`RestartInstance`). Если запуск не удался, продолжает работать старый.
- Порты моста занимаются на всё время жизни конфигурации, чтобы соединение, пришедшее во время перезапуска, не попало на закрытый порт.

**Для JOXY:** в 0.3.2 мы пересобираем сессию после первой неудачной проверки. Следующий шаг — реагировать на само событие смены сети (без ожидания проверки) и делать замену «сначала новый, потом гасим старый». Тогда переподключение не будет обрывать соединения дольше необходимого.

### 4. Ядро проверяет родителя и само за собой убирает
`core/main.go`, `core/internal/parentcheck/`

- При старте ядро проверяет, что родитель — именно `Throne.exe` из той же папки. Чужая программа не сможет управлять ядром, запущенным с правами администратора.
- Ядро ждёт завершения родителя (на Windows — `Wait` по дескриптору) и выходит вслед за ним.
- При старте ядро подчищает следы прошлого сбоя (`guard.CleanupStale`, `sysdns.RestoreStale`), так же как наша очистка `runtime/` в 0.3.2.
- Сторож памяти: при живой куче больше 1,5 ГБ после принудительной сборки мусора ядро пишет профиль и падает с понятной ошибкой, а не тормозит систему.
- Временные файлы привилегированного процесса создаются только через `CreateTemp`: предсказуемое имя позволяет подменить его символической ссылкой.

**Для JOXY:** watchdog-скрипты сейчас опрашивают PID раз в секунду. Ожидание дескриптора процесса надёжнее и не тратит ресурсы. Проверка «кто меня запустил» станет нужна, если появится отдельный помощник с правами администратора.

### 5. Системный прокси Windows — через WinINet, по всем подключениям
`src/sys/windows/SystemProxy.cpp`

- WinINet хранит отдельные настройки для LAN и для каждого dial-up/PPPoE/VPN-подключения и использует настройки активного. Throne переключает их все и запоминает исходные флаги автоопределения и PAC для каждого.
- Флаги нужно читать из `FLAGS_UI` (с запасным `FLAGS`), а писать всегда в `FLAGS`. Так рекомендует Microsoft.
- Исходные флаги пользователя запоминаются только при первом включении, иначе при повторном применении сохранились бы уже наши.

**Для JOXY:** `windows-proxy.ps1` правит реестр только для LAN. Проверить поведение при активном PPPoE или VPN-подключении и перейти на `InternetSetOption` с `INTERNET_PER_CONN_*`.

### 6. Обнаружение чужого TUN
`src/sys/HostTun.cpp`

- После сбоя остаются отключённые адаптеры `throne-tun N`. Throne считает живым только адаптер в состоянии Up, как и наш `tunnels.mjs` после 0.3.1.

### 7. Проверки задержки
`core/internal/probe/urltest.go`

- Пакетная проверка с ограничением параллельности и опцией «дважды»: первый запрос прогревает соединение, засчитывается второй. Наша задержка сейчас включает установку TLS/REALITY и выглядит хуже реальной.

## План для JOXY

1. **0.4.0 — помощник `joxy-guard`** (Go, свой код): kill switch на динамической сессии WFP + ожидание родителя по дескриптору. Не используется, пока не включён в настройках.
2. **0.4.x — TUN без PowerShell:** сначала проверить автомаршруты TUN в Xray 26.x на Windows. Если их не хватает — sing-box только для TUN через SOCKS-мост в Xray. После этого удалить `windows-tun.ps1` и журнал восстановления.
3. **0.4.x — смена сети по событию** и замена ядра «новое поднялось → старое закрыли».
4. **Позже:** системный прокси через WinINet для всех подключений; двойной замер задержки.
